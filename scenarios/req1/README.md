# 변경 요청 1: 대기열 늘리기

## 요청 내용 (상품기획팀)

저녁 시간대(19~21시)에 기기 이벤트가 한꺼번에 몰리면 허브가 이벤트를 거부합니다(`REJECTED_FULL`). 현장 로그를 보면 동시에 대기하는 이벤트는 최대 32개입니다.

- 대기 이벤트를 최소 32개까지 받을 수 있게 한다.
- 허브 보드 메모리(64MB)가 작으므로, 평소에는 지금처럼 8칸만 쓰고 필요할 때만 늘린다.
- `EventQueue` 인터페이스와 Java 8 호환성은 유지한다.

## 바꾸면 안 되는 것 (안전 검토 SR-2017-11)

| 번호 | 내용 |
|---|---|
| R1 | 대기 이벤트 수는 승인된 상한을 넘지 않는다. |
| R2 | 누수·과열(critical) 이벤트는 절대 거부하지 않는다. |
| R3 | 큐에 남는 이벤트의 상대 순서는 바뀌지 않는다. 밀어낼 때는 가장 오래된 비중요 이벤트를 밀어낸다. |
| R4 | 비중요 이벤트는 큐가 가득 차 있고 autoDrain이 꺼져 있을 때만 거부한다. |

이번 요청에서 승인된 것은 **R1의 상한 값을 8에서 32로 바꾸는 것뿐**입니다. 그 밖의 동작 변화는 별도 승인이 필요합니다. 이 계약은 `formal/Dispatcher.dfy`의 `Submit` 사후조건으로 적혀 있습니다.

## 제공되는 파일

| 폴더 | 내용 |
|---|---|
| `ai-A/` | 패치 A. 큐가 가득 차면 배열을 2배로 늘림. `grow()`가 배열을 통째로 복사하고 head는 그대로. AI가 고친 테스트와 새 테스트 2개 포함 |
| `ai-B/` | 패치 B. 배열을 늘릴 때 오래된 것부터 순서대로 복사(head = 0). 상한 32는 Dispatcher와 Watchdog이 설정값 `dispatch.maxPending`으로 직접 가짐 |
| `ai-A-oldtests/` | 패치 A의 제품 코드만 있고 테스트는 레거시 그대로. AI가 테스트를 고치기 전이면 어떻게 되는지 보는 용도(테스트 5개 실패) |
| `model/` | Dafny 모델: `RingQueue_A.dfy`(패치 A의 대기열), `RingQueue.dfy`·`Dispatcher.dfy`(패치 B의 대기열과 Dispatcher) |

패치 A는 테스트 40개, 패치 B는 42개(각자 고치거나 더한 것 포함)를 전부 통과합니다. 패치 A는 Dafny 증명과 차분 테스트에서 걸리고, 패치 B는 통과합니다.

직접 Codex로 만든 패치도 같은 방법으로 확인할 수 있습니다. 예: `cp -r legacy mywork`로 복사한 뒤 Codex에게 mywork를 고치게 하고, `make variant-test V=mywork`, `make impact V=mywork`를 실행합니다.

실습 순서와 결과 해설은 `docs/LAB_GUIDE.md`의 실습 C에 있습니다.
