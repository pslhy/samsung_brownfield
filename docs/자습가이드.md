# HomeHub 실습 자습 가이드: 도구를 직접 다루며 처음부터

노트북도, 실습 실행 명령(`make`, Windows에서 make 대신 쓰는 `SETUP/make_fallback.py`)도 쓰지 않습니다. **javac, java, dafny**와 실습의 분석 도구(`tools/*.py`)를 직접 실행하면서 실습 A~E를 처음부터 끝까지 따라갑니다. 실습에서 AI에게 시키는 일(패치, Dafny 모델 등)은 손으로 직접 해 보거나, 저장소에 들어 있는 **모범 답안**(AI가 만든 결과)을 씁니다. Codex 없이 끝까지 따라갈 수 있습니다. 단계마다 실습생이 직접 판단할 일과 AI에게 맡기는 일을 표시해 두었습니다(아래 "단계 표시").

읽기용 해설은 `docs/LAB_GUIDE.md`에 있습니다. 이 문서는 "무엇을 치고, 어디를 고치고, 무엇이 나와야 하는가"만 다룹니다. 아래의 예상 결과는 모두 macOS에서 이 문서의 명령을 그대로 실행해 얻은 값입니다.


이 실습에서 다루는 질문은 하나입니다.

> **AI가 고친 코드가 기존 동작을 지켰는지, 무엇으로 어떻게 확인하는가?**

| 실습 | 질문 | 확인 도구 |
|---|---|---|
| A. 변경 영향 | 이 변경이 어디까지 영향을 주는가? 도구가 놓치는 곳은? | 동작 기록 비교, def-use 영향 분석 |
| B. Dafny 모델 | AI가 만든 Dafny 모델을 믿어도 되는가? | 계약 읽기, Dafny 검증, 차분 테스트 |
| C. AI 패치 판단 | 테스트를 다 통과한 AI 패치 2개 중 무엇을 내보낼 수 있는가? | 테스트, Dafny 검증, 차분 테스트 |
| D. 재검증 범위 | 코드가 바뀔 때마다 증명을 전부 다시 해야 하는가? | 바뀐 것의 종류로 재검증 범위 줄이기 |
| E. 정리 규칙 | 코드 정리 규칙을 일괄 적용해도 동작이 그대로인가? | 규칙의 조건 적기, 테스트, 동작 기록 비교 |

## 들어가기 전에

### 필요한 것

JDK 11(저장소의 `legacy/build`를 만든 것과 같은 버전), Dafny 4.11, Python 3. 없으면 `python3 SETUP/setup.py`(Windows: `python SETUP\setup.py`)로 설치합니다. OS를 보고 알맞은 설치 스크립트를 실행합니다. Windows에 Python이 아직 없으면 대신 `SETUP\setup_windows.bat`을 더블클릭합니다(Python도 설치). 설치 도구는 JDK와 Dafny를 실습 폴더 안의 `jdk/`, `dafny/`에 풀고, 마지막 단계에서 Codex CLI(선택)를 내 계정에 설치하거나 업데이트합니다. Codex를 다시 설치하거나 업데이트하려면 `python3 SETUP/setup.py --update-codex`(이미 설치된 부분은 건너뜀).

**터미널을 열 때마다, 실습 폴더 맨 위에서 한 번** 실습 폴더의 JDK와 Dafny를 PATH 맨 앞에 둡니다. PC에 다른 JDK나 Dafny가 있어도 이 실습에서는 항상 이것을 쓰게 하기 위해서입니다. A-1처럼 바이트코드를 비교하는 단계는 레거시와 내 코드를 **같은 javac**로 빌드해야 숫자가 맞습니다.

macOS (bash, zsh):
```
export JAVA_HOME="$PWD/jdk/Contents/Home"
export DAFNY="$PWD/dafny/dafny"
export PATH="$JAVA_HOME/bin:$PWD/dafny:$PATH"
```

Linux에서 JDK를 `jdk/`에 직접 풀었다면 첫 줄만 `export JAVA_HOME="$PWD/jdk"`로 바꿉니다.

Windows (cmd):
```
set "JAVA_HOME=%CD%\jdk"
set "DAFNY=%CD%\dafny\dafny.exe"
set "PATH=%CD%\jdk\bin;%CD%\dafny;%PATH%"
```

확인합니다. 경로가 모두 실습 폴더 안이어야 합니다(cmd: `where javac dafny`의 각 첫 줄).

```
command -v java javac dafny   # <실습 폴더>/jdk/.../bin/java, .../javac, <실습 폴더>/dafny/dafny
java -version        # openjdk version "11.0.32.1" ...
javac -version       # javac 11.0.32.1
dafny --version      # 4.11.0+...
python3 --version    # Python 3.x   (Windows: python --version)
```

### 규칙

- 모든 명령은 **실습 폴더 맨 위**에서 실행합니다. 명령은 모두 한 줄입니다(줄이 길어 보여도 한 줄로 붙여 넣습니다).
- 직접 만드는 것은 아래 네 폴더에만 둡니다. 이 폴더들에는 모범 답안으로 미리 만들어 둔 결과도 저장소에 함께 들어 있습니다(실습이 막힐 때 이어 가는 데 씁니다). 그래서 실습을 하면 `git status`에 바뀐 파일이 많이 나오는데, 정상입니다. 폴더째 지우지 말고, 시작할 때 0-0에서 백업해 둔 뒤 끝나면 맨 끝의 "끝나고 정리하기"대로 되돌립니다.

  | 폴더 | 무엇을 |
  |---|---|
  | `work/<이름>/` | 레거시를 통째로 복사한 프로젝트. 여기서 고치고 빌드합니다 |
  | `build/` | Dafny 모델을 Java로 바꾼 jar, 차분 테스트 도구 |
  | `out/` | 분석 결과(`out/html/*.html` 보고서, `.json`, `.md`) |
  | `mine/` | B-1에서 AI가 만든 Dafny 모델과 연결 코드. 처음부터 예시 파일이 들어 있고, B-1 2단계에서 덮어씁니다 |

- `legacy/`(원본)를 직접 고치는 단계가 한 번(B-3), `rewrite/RewriteRules.dfy`를 고치는 단계가 한 번(E-3) 있습니다. 끝나면 **반드시 되돌립니다**.
- 분석 도구는 보고서를 만들면 브라우저로 엽니다. 열지 않으려면 터미널을 열 때마다 `export HH_OPEN=0`(cmd: `set HH_OPEN=0`).

### 단계 표시

단계마다 맨 앞에 누가 무엇을 하는지 표시해 두었습니다.

| 표시 | 하는 사람 | 하는 일 |
|---|---|---|
| **[실행]** | 실습생 | 적힌 명령을 그대로 실행하거나 적힌 대로 고치고, 결과가 "예상"과 같은지만 봅니다. 다르면 그 단계의 안내를 보고, 그래도 다르면 보조강사를 부릅니다 |
| **[직접 확인]** | 실습생 (AI에게 맡기지 않음) | 코드, 계약, 보고서를 읽고 맞는지 스스로 판단합니다. 이 실습에서 익히는 부분입니다 |
| **[AI 몫]** | 실습에서는 AI(Codex). 직접 해도 됨 | 노트북 실습에서는 요청서나 `docs/PROMPTS.md`의 프롬프트를 AI에게 주고 받는 결과입니다. 이 문서에서는 직접 쓰거나 모범 답안(아래 "모범 답안이 있는 곳")을 씁니다. 누가 만들었든 결과는 뒤의 [직접 확인]에서 사람이 검사합니다 |

### [AI 몫] 단계를 하는 두 가지 방법

[AI 몫] 단계에는 접힌 상자가 두 개 있습니다. 둘 중 하나만 펼쳐서 따라 합니다.

- **방법 1: 직접 고치기.** 고칠 파일과 줄, 바꿀 내용이 적혀 있습니다. 그대로 따라 하면 모범 답안과 같아지고, 뒤 단계의 결과도 이 문서의 "예상"과 같습니다.
- **방법 2: Codex에게 시키기.** 회사 보안 정책이 허용할 때만 씁니다. 상자에 적힌 폴더에서 Codex를 열고 예시 프롬프트를 붙여 넣습니다. Codex의 결과는 매번 다르고 모범 답안과 다를 수 있습니다. 그래서 뒤 단계의 숫자가 "예상"과 다를 수 있습니다. 상자의 "확인" 명령으로 모범 답안과 무엇이 다른지 보고, 그 차이가 뒤 단계의 결과를 어떻게 바꾸는지 보는 것도 실습입니다.

Codex를 쓰는 순서(모든 [AI 몫] 단계 공통):

1. 처음 한 번: `python3 SETUP/setup.py`(Windows: `python SETUP\setup.py`)가 마지막 단계에서 Codex를 설치합니다. 설치한 뒤 `codex login`으로 로그인합니다.
2. 터미널에서 "필요한 것"의 `export`(cmd: `set`) 세 줄을 실행해 둡니다. Codex가 `javac`나 `dafny`를 실행할 때도 실습 폴더의 것을 쓰게 됩니다.
3. 실습 폴더 맨 위에서, 상자에 적힌 폴더를 지정해 Codex를 엽니다: `codex -C <폴더>`. 기본 설정에서 Codex는 그 폴더 안의 파일만 고칠 수 있고, 다른 폴더는 읽기만 합니다.
4. 예시 프롬프트를 붙여 넣습니다. 파일을 고치거나 명령을 실행하겠다고 물으면 내용을 보고 허락합니다.
5. 끝나면 `/quit`으로 나옵니다. 상자의 "확인" 명령으로 무엇이 바뀌었는지 봅니다. 고치라고 한 파일 말고 다른 파일이 바뀌었으면 그 변경은 되돌립니다.

노트북에서는 `lab.codex("P-1")`처럼 부르면 `docs/PROMPTS.md`의 프롬프트로 같은 일을 합니다.

### 이 문서를 읽는 법

실습(0, 1, A~E)은 모두 같은 모양입니다.

- 맨 위: **배울 것**(이 실습의 요점 한 문장), **상황**, **순서**
- 단계마다: **이 단계의 질문** → 할 일(명령) → 결과 보기 → **알게 된 것**

결과를 보는 곳에는 접힌 상자가 두 개 있습니다. 편한 쪽 하나를 펼칩니다.

- **HTML 보고서로 보기**: 실습이 제공하는 도구(`tools/*.py` 등)로 결과를 HTML 보고서로 만들어 봅니다. 명령의 마지막 줄이 보고서를 만들고 브라우저로 엽니다.
- **도구 없이 검토하기**: `git diff`, `javap`, `diff`, `dafny verify` 같은 기본 명령으로 직접 확인합니다. 도구는 손으로도 할 수 있는 일을 빠르고 빠짐없이 해 줄 뿐이므로, 한 번은 이쪽으로 따라 해 보며 도구가 무엇을 세는지 확인해 보세요. 단, `[실행]` 단계의 "예상"에 적힌 숫자(예: `메서드 2, 데이터 0, 테스트 0/38`)는 "HTML 보고서로 보기"의 도구 명령이 화면에 찍는 값입니다. "도구 없이 검토하기"로 하면 이 숫자는 나오지 않고, 같은 결론을 손으로 확인합니다.

빌드·테스트처럼 꼭 해야 하는 명령과, 뒤 단계가 쓰는 결과 파일을 만드는 명령은 상자에 넣지 않고 본문에 둡니다.

### Windows(cmd)에서 바꿔 칠 것

이 문서의 명령은 macOS·Linux(bash, zsh) 모양입니다. Windows에서는 **명령 프롬프트(cmd)**를 열고 아래만 바꿉니다. (Windows 모양은 아직 실제로 돌려 보지 않았습니다.)

먼저 터미널을 열 때마다 한 번(위 "필요한 것"의 `set` 세 줄과 함께):

```
set PYTHONUTF8=1
```

도구가 UTF-8로 된 소스와 기록 파일을 읽기 때문입니다. 실습 폴더 경로에는 **공백이 없어야** 합니다(예: `C:\lab`). 아래의 소스 목록 파일이 경로를 따옴표로 감싸지 않기 때문입니다.

| macOS·Linux | Windows cmd |
|---|---|
| `python3` | `python`. **`python3`라고 치면 안 됩니다**: Windows의 `python3`는 Microsoft Store 안내용 가짜 실행 파일이라 `Python` 한 단어만 찍고 끝납니다. `python`도 그렇다면(`where python`의 첫 줄이 `...\WindowsApps\...`) 설정 → 앱 → 고급 앱 설정 → 앱 실행 별칭에서 `python.exe`·`python3.exe`를 끄거나, `.venv\Scripts\python`으로 칩니다 |
| `export HH_OPEN=0`, `P=legacy` | `set HH_OPEN=0`, `set P=legacy` (`=` 뒤에 공백을 두지 않음) |
| `$P` | `%P%` |
| 클래스 경로 구분 `a:b:c` | `a;b;c` (따옴표 필요 없음) |
| `$(find D -name '*.java')` (소스 전체) | 먼저 `dir /s /b D\*.java > 목록.txt`, 그리고 그 자리에 `@목록.txt` (아래 명령 묶음 참고) |
| `difftest/src/difftest/*.java` | `dir /s /b difftest\src\difftest\*.java > build\difftest-src.txt` 후 `@build\difftest-src.txt` |
| `rm -rf X` | `if exist X rmdir /s /q X` |
| `mkdir -p X Y` | `mkdir X Y` (중간 폴더도 만듦. 이미 있으면 오류 문구만 나오고 넘어감) |
| `cp -r legacy work/x` (폴더 복사) | `xcopy /e /i /q legacy work\x` |
| `cp -r scenarios/req1/ai-A/src work/req1-ai-A/` (덮어쓰기) | `xcopy /e /i /q /y scenarios\req1\ai-A\src work\req1-ai-A\src` |
| `cp A B` (파일 복사) | `copy A B` |
| `printf '...' > 파일` | 메모장으로 그 파일을 만들고 내용을 적음 |
| `명령 \| head -1`, `명령 \| tail -1` | `명령 > work\out.txt` 후 메모장으로 첫 줄·끝 줄을 봄 |
| 경로의 `/` | `java`·`javac`·`python`·`dafny`·`git`의 인자는 `/` 그대로 됨. `dir`·`xcopy`·`rmdir`·`copy`·`mkdir`에는 `\` |
| `git checkout -- F`, `git diff --no-index A B` | 같음 (git이 없으면 편집기로 되돌리고, VS Code "선택한 항목 비교"로 비교) |

### 빌드하고 테스트하는 명령 묶음

실습 내내 쓰는 다섯 줄입니다. 각 단계에는 첫 줄의 `P=`를 채운 명령이 그대로 적혀 있으니 복사해 붙여 넣으면 됩니다(Windows cmd용은 그 아래 "Windows cmd" 상자). 여기서는 각 줄이 무슨 일을 하는지 설명합니다.

```
P=legacy
rm -rf $P/build && mkdir -p $P/build/classes $P/build/test-classes
javac -nowarn -Xlint:-options -encoding UTF-8 --release 8 -d $P/build/classes $(find $P/src/main/java -name '*.java')
javac -nowarn -Xlint:-options -encoding UTF-8 --release 8 -cp $P/build/classes -d $P/build/test-classes $(find $P/src/test/java -name '*.java')
java -cp $P/build/classes:$P/build/test-classes com.dxlab.homehub.testkit.TestRunner
```

| 줄 | 하는 일 |
|---|---|
| 2 | 지난 빌드를 지우고 빈 폴더를 만듭니다 |
| 3 | 제품 코드 전체를 컴파일합니다. `--release 8`: Java 8 코드로(레거시가 Java 8). `-encoding UTF-8`: 소스의 한글 주석. `-nowarn -Xlint:-options`: 경고 끄기 |
| 4 | 테스트 코드 전체를 컴파일합니다. 제품 코드를 `-cp`로 봅니다 |
| 5 | 사내 테스트 실행기(JUnit 이전에 만든 것)가 `test`로 시작하는 메서드를 모두 돌립니다. 마지막 줄이 `tests: N, passed: N, failed: 0` |

Windows cmd에서는(폴더 이름의 `/`를 `\`로: `set P=work\my-req2`):

```
set P=legacy
if exist %P%\build rmdir /s /q %P%\build
mkdir %P%\build\classes %P%\build\test-classes
dir /s /b %P%\src\main\java\*.java > %P%\build\main-src.txt
dir /s /b %P%\src\test\java\*.java > %P%\build\test-src.txt
javac -nowarn -Xlint:-options -encoding UTF-8 --release 8 -d %P%\build\classes @%P%\build\main-src.txt
javac -nowarn -Xlint:-options -encoding UTF-8 --release 8 -cp %P%\build\classes -d %P%\build\test-classes @%P%\build\test-src.txt
java -cp %P%\build\classes;%P%\build\test-classes com.dxlab.homehub.testkit.TestRunner
```

`dir /s /b`가 소스 파일 목록을 파일로 쓰고, javac는 `@파일`로 그 목록을 읽습니다.

## 1. 코드 둘러보기

> **이 실습에서 할 것: HomeHub가 무엇을 하는지, 메시지 한 줄이 어떻게 처리되는지 보고, 동작이 그대로인지 확인하는 방법(동작 기록 비교)을 익힙니다.**

**상황.** HomeHub는 이 실습을 위해 만든 가상의 가전 허브 프로그램입니다. 세탁기, 냉장고, 에어컨, 누수센서 같은 가전이 보내는 메시지를 받아 처리합니다. 2014~2017년에 여러 사람이 고쳐 온 Java 8 코드라는 설정입니다(30개 타입, 약 1,600줄, 테스트 38개).

**순서.** 1-1 구조 지도와 자주 보는 코드 → 1-2 허브를 직접 돌려 보기 → 1-3 동작 기록 비교 → 1-4 (참고) 공유 상태와 설정값

### 1-1. 구조 지도와 자주 보는 코드

**이 단계의 질문:** HomeHub는 어떤 부품으로 이뤄져 있고, 실습에서 자주 보는 코드는 어디인가?

**[직접 확인]** 브라우저로 `docs/homehub_구조.html`(HomeHub 구조 지도)을 엽니다. 지도를 확대하듯 봅니다. ⊕ 표시가 있는 상자를 누르면 그 안의 자세한 그림이 나오고, 위의 경로나 "← 밖으로"를 누르면 나옵니다. 처음에는 이 순서로 봅니다(약 15분).

1. 바깥 그림: HomeHub가 무엇을 받고 무엇을 남기는지
2. 가운데 HomeHub 상자를 눌러 안의 부품 보기
3. "▶ 메시지 하나 따라가기": 메시지 한 줄이 어느 부품을 거쳐 처리되는지 한 단계씩
4. 궁금한 부품(특히 대기열, 접수·꺼내기)을 눌러 보기

다 외울 필요는 없습니다. 실습 중에 낯선 부품이 나오면 그때 다시 열어 봅니다.

편집기로 열어 둘 파일입니다. 경로는 모두 `legacy/src/main/java/com/dxlab/homehub/` 아래입니다.

| 파일 | 볼 줄 | 내용 |
|---|---|---|
| `queue/RingEventQueue.java` | 30~45, 64~76 | 원형 대기열(기본 8칸). `offer`, `poll`, `clear`, `snapshot` |
| `dispatch/Dispatcher.java` | 41~79, 85~97 | `submit`(받을지 결정, 규칙 R1~R4), `evictOldestNonCritical`(밀어내기) |
| `ops/Watchdog.java` | 22 | 대기열이 75% 이상 찼는지 보는 조건 |
| `device/DeviceRegistry.java` | 52~56 | 기기 목록 정렬 비교 함수 |

대기열이 가득 찼을 때 바꾸면 안 되는 규칙 R1~R4입니다. 실습 B, C, E에서 다시 나옵니다.

| 번호 | 규칙 |
|---|---|
| R1 | 대기 이벤트 수는 정해진 상한을 넘지 않는다 |
| R2 | 누수·과열 같은 중요(critical) 이벤트는 절대 거부하지 않는다 |
| R3 | 대기열에 남는 이벤트의 순서는 바뀌지 않는다. 자리를 만들어야 하면 가장 오래된 비중요 이벤트를 밀어낸다 |
| R4 | 비중요 이벤트는 대기열이 가득 차 있고 autoDrain 설정이 꺼져 있을 때만 거부한다 |

**autoDrain 설정**(`dispatch.autoDrainOnFull`, 기본값 꺼짐)은 대기열이 가득 찼을 때 비중요 이벤트를 어떻게 할지 정합니다. 켜져 있으면 Dispatcher가 대기열에서 가장 오래된 이벤트 하나를 그 자리에서 바로 처리해(처리기로 넘겨) 자리를 만들고 새 이벤트를 받습니다. 꺼져 있으면 새 이벤트를 거부합니다(`REJECTED_FULL`). 중요 이벤트는 이 설정과 상관없이 R2대로 늘 받습니다.

실습에서 다루는 변경 요청은 두 건입니다.

| 이름 | 폴더 | 요청 내용 |
|---|---|---|
| 변경 요청 1: 대기열 늘리기 | `scenarios/req1` | 저녁에 이벤트가 몰리면 거부된다. 최대 32개까지 받게 해 달라 |
| 변경 요청 2: 대기열 연산 빠르게 | `scenarios/req2` | 허브 칩에서 `%` 연산이 느리다. 대기열 코드에서 `%`를 없애 달라(동작은 그대로) |

각 폴더에는 AI가 만든 Java 패치(`ai*/`)와 Dafny 모델(`model/`)이 있습니다. 패치 폴더에는 바뀐 파일만 있어서, 실행할 때는 레거시 전체를 복사한 뒤 그 위에 덮어써서 빌드합니다.

**알게 된 것:** 실습의 중심은 대기열(`RingEventQueue`)과 그것을 쓰는 접수(`Dispatcher`)입니다.

## A. 변경 영향 분석

> **이 실습에서 배울 것: 코드를 고치면 무엇을 다시 확인해야 하는지 알아야 합니다.** 영향 분석 도구는 바뀐 줄에서 나온 값이 어디까지 흘러가는지 끝까지 따라가 빠짐없이 찾아 줍니다. 대신 넓게 잡고, 라이브러리가 대신 부르는 코드는 따라가지 못합니다.

**순서.**
- **A-1.** 변경 요청 2의 패치를 직접 만들고 영향 보고서를 읽습니다. 도구는 놓치지 않으려고 넓게 잡으므로, 괜히 들어간 테스트를 AI로 걸러 냅니다.
- **A-2.** 도구가 찾아 주는 것(① 코드가 그대로인 곳의 영향)과 못 찾는 것(② 라이브러리가 대신 부르는 코드)을 사례 하나씩으로 봅니다.

부품 이름이 낯설면 1-1의 구조 지도(`docs/homehub_구조.html`)를 다시 엽니다.

### A-1. 변경 영향 보고서 읽기 (변경 요청 2)

**이 단계의 질문:** 코드를 고치면 무엇을 다시 확인해야 할까?

영향 분석 도구는 **바뀐 줄에서 계산한 값이 어디까지 흘러가는지**(def-use: 값을 만드는 곳 → 쓰는 곳)를 끝까지 따라갑니다.

- 바뀐 줄에서 계산한 값 → 그 값을 저장한 필드·배열·컬렉션 → 그것을 읽는 줄
- 그 값으로 계산한 반환값 → 그 반환값을 받아 쓰는 줄
- 그 값으로 판단하는 `if`·반복문 → 그 안에서 일어나는 모든 일(필드 쓰기, 메서드 호출)

메서드를 넘나들 때는 **부른 곳으로만 돌아가도록** 짝을 맞춥니다. 예를 들어 메서드 `m(x)`를 A와 B가 부른다고 합시다. A가 넘긴 값 때문에 `m`의 반환값이 달라져도, 그 영향은 A로만 돌아가고 B에게는 가지 않습니다.

**대상: 변경 요청 2.** 플랫폼팀이 "허브 칩에서 나눗셈(`%`)이 느리니, 대기열 `RingEventQueue`에서 `%`를 없애 달라. 동작은 바꾸지 말 것"이라고 요청했습니다. 실습에서는 AI가 `offer`, `poll`, `clear`, `snapshot` 네 메서드를 고친 패치를 씁니다. 여기서는 그 패치를 직접 만들어 보고 영향을 분석합니다.

**[직접 확인] 1단계: 요청 읽기.** `scenarios/req2/README.md`. `RingEventQueue`의 offer / poll / snapshot에서 `%`를 없애고, `clear()`는 poll을 반복하지 않고 한 번에 비운다. 동작은 바꾸지 않는다.

**[실행] 2단계: 레거시를 통째로 복사.**

   ```
   git diff --no-index legacy/src/main/java work/my-req2/src/main/java
   javap -c -p -cp legacy/build/classes com.dxlab.homehub.queue.RingEventQueue > out/base.txt
   javap -c -p -cp work/my-req2/build/classes com.dxlab.homehub.queue.RingEventQueue > out/changed.txt
   diff out/base.txt out/changed.txt
   ```
2. 바뀐 줄이 쓰는 필드(`head`, `count`, `buf`)마다 편집기의 "모든 참조 찾기"로 읽는 곳을 찾습니다. 읽은 값이 반환되거나 조건(`if`, `while`)에 쓰이면, 그 메서드를 부르는 곳을 "호출 계층 표시"로 찾아 같은 일을 반복합니다.
3. 이렇게 닿은 메서드를 부르는 테스트 메서드를 "호출 계층 표시"로 찾으면, 그것이 다시 돌릴 테스트입니다.

**[직접 확인] 6단계: 왜 들어갔는지 물어보기.** 특정 메서드나 테스트가 왜 들어갔는지는 `--why`로 물어봅니다. 전체 보고서 대신 그 이유만 보여 줍니다. **위에서 아래로** 읽습니다. 노란 점이 바뀐 줄이고, 그 아래로 값이 지나간 코드 줄이 이어집니다. 줄 사이의 회색 글은 값이 어떻게 넘어갔는지입니다. 서로 다른 바뀐 메서드에서 출발하는 이유가 있으면 "다른 이유"로 3가지까지 보여 줍니다.

먼저 전력 승인 `power.PowerBudget#tryStart`를 물어봅니다. 첫 번째 이유: `poll`의 바뀐 줄 `head++`가 필드 `head`를 바꿉니다 → `poll`이 꺼내는 이벤트(44줄)가 달라질 수 있습니다 → `dispatchOne`이 꺼낸 이벤트가 `null`인지에 따라(102줄) 처리기를 부를지가 달라집니다 → `DeviceStatusHandler`가 `tryStart`를 부를지(54줄) → 승인 목록 `running`에 쓰는 값(32줄)이 달라질 수 있습니다.

다음으로 도구가 고른 테스트 중 하나인 `EventParserTest#testBasicLine`을 물어봅니다. 이 테스트(`legacy/src/test/java/com/dxlab/homehub/EventParserTest.java` 10~16줄)는 글자 한 줄을 이벤트로 바꾸고 번호(`seq`)·기기·종류가 맞는지 확인할 뿐, **대기열은 만들지도 쓰지도 않습니다.** 그런데도 들어간 이유는, 도구가 `Event`의 `seq` 칸을 **이벤트 객체마다 따로 보지 않고 하나의 칸으로** 보기 때문입니다.

| | 실제로 일어나는 일 | 도구가 보는 것 |
|---|---|---|
| 쓰는 곳 | 대기열이 꺼내 준 이벤트를 보고, 규칙 검사가 과열 이벤트를 **새로 만들며** `seq`를 씀 (`legacy/src/main/java/com/dxlab/homehub/rules/RuleEngine.java` 48줄 `new Event(nextSeq++, ...)`) | "`Event.seq`에 쓰는 값이 달라질 수 있다" |
| 읽는 곳 | 테스트는 **자기가 만든 다른 이벤트**의 `seq`를 읽음 (`EventParserTest` 13줄 `e.getSeq()`) | "`Event.seq`를 읽으니 영향받는다" |
| 결론 | 서로 다른 객체라 **상관없음** | **영향 있음** → 다시 돌릴 테스트에 넣음 |

도구는 하나도 놓치지 않는 쪽을 택해서 이렇게 "괜히 들어간" 테스트가 생깁니다.

## B. AI가 만든 Dafny 모델 믿기

> **이 실습에서 배울 것: AI가 만든 Dafny 모델이 검증을 통과해도, 그것만으로 믿을 수는 없습니다.** 확인되는 것은 "모델이 계약을 지킨다"까지입니다. 계약이 맞게 쓰였는지는 사람이 읽어서, 모델이 Java와 같게 동작하는지는 차분 테스트로 따로 확인합니다.

Java 코드는 그대로 두고, 그 옆에 **같은 일을 하는 Dafny 코드**(그림자 모델)를 둡니다. Dafny는 각 메서드에 적힌 계약(지켜야 할 약속)을 코드가 정말 지키는지 **모든 입력에 대해** 증명합니다. 읽을 때 필요한 문법은 이것뿐입니다.

| 문법 | 뜻 |
|---|---|
| `requires P` | 이 메서드를 부르기 전에 P가 참이어야 한다 (사전조건) |
| `ensures Q` | 이 메서드가 끝나면 Q가 참이다 (사후조건) |
| `old(x)` | 메서드가 시작될 때의 x 값 |
| `ghost var elems: seq<Event>` | 증명에만 쓰는 변수. 실행되지 않습니다. 여기서는 "대기열에 든 이벤트 목록(오래된 것부터)" |
| `modifies x` | 이 메서드가 바꿀 수 있는 것 |
| `A ==> B` / `A <==> B` | A이면 B / A와 B는 같이 참이거나 같이 거짓 |

증명이 통과해도 확인되는 것은 "Dafny 모델이 계약을 지킨다"까지입니다. 그래서 두 가지를 따로 확인합니다.
1. **계약이 맞게 쓰였는가**: 사람이 읽어서 판단합니다. 계약이 약하면 틀린 코드도 증명을 통과합니다.
2. **모델이 Java와 같게 동작하는가**: 차분 테스트로 확인합니다.

**순서.** B-1 AI가 만든 대기열 모델을 검증·차분 테스트하고 계약을 읽기 → B-2 Dispatcher 모델의 계약에서 규칙 R1~R4 찾기 → B-3 Java에 버그를 넣고 차분 테스트가 잡는지 보기

### B-1. AI가 만든 모델 읽기

**이 단계의 질문:** AI가 만든 대기열 모델을 믿어도 되는가?

AI에게 아래 한 문장과 `RingEventQueue.java`만 주고 Dafny 모델을 만들게 했습니다(프롬프트 P-1). 일부러 아주 짧게 물었습니다.

> 다음 Java 클래스를 Dafny로 만들어 줘. dafny verify가 통과해야 해.

**[실행] 1단계: 차분 테스트 도구 빌드 (처음 한 번).** 차분 테스트는 같은 입력을 두 구현에 넣고 결과가 같은지 비교하는 테스트입니다. 이 실습의 차분 테스트 도구(`difftest/`)에는 두 가지가 있습니다.

**[직접 확인] 4단계: 계약 읽기.** `mine/RingEventQueue.dfy`를 처음부터 끝까지 읽습니다. 줄마다 무엇인지 표로 정리했습니다. **사전조건·바꿀 수 있는 것·사후조건(계약)이 사람이 꼭 읽고 판단할 부분**이고, 증명 도우미는 건너뛰어도 됩니다.

| 줄 | 종류 | 뜻 |
|---|---|---|
| 13 | 클래스 | Java 클래스 `RingEventQueue`를 옮긴 Dafny 클래스 |
| 14~16 | Java 필드 | Java 필드 `buf`, `head`, `count`를 그대로 옮긴 것. 실행되는 코드 |
| 17 | 증명용 변수 | 대기열에 든 이벤트 목록, 오래된 것부터. 실행되지 않고 증명에만 씀. 아래 계약은 모두 배열 대신 이 목록으로 말함(맨 뒤에 추가된다, 맨 앞이 빠진다) |
| 19~21 | 불변식 | `Valid()`: 배열과 `elems`가 서로 맞는다는 약속. 모든 메서드가 시작할 때 이것을 믿고, 끝날 때 다시 지켜야 함 |
| 22~25 | 불변식 | 칸이 1개 이상, `head`는 배열 안, `count`는 0~칸 수, `elems`의 길이 = `count` |
| 26~27 | 불변식 | **핵심**: `elems`의 i번째 = 배열의 `(head + i) % 칸 수`번째 칸. 끝을 넘으면 앞으로 돌아감(아래 그림) |
| 29~32 | 생성자 | Java `RingEventQueue(int capacity)`. `capacity > 0`일 때만 부를 수 있음(Java는 이 경우 예외). 끝나면 `Valid()`, `elems`는 빈 목록, 칸 수 = `capacity`, `fresh(buf)`: 새로 만든 배열 |
| 40 | `Offer` | Java `offer(Event e)`. 결과 `r`은 OK / FULL / REJECTED |
| 41 | 사전조건 | `Valid()`일 것. 이것 말고는 조건이 없으므로 가득 찼을 때도 부를 수 있음 |
| 42 | 바꿀 수 있는 것 | 이 객체의 필드(`this`)와 배열의 내용(`buf`) |
| 43 | 사후조건 | 끝나면 다시 `Valid()`, 같은 배열(`buf == old(buf)`: 새 배열로 바꾸지 않음) |
| 44 | 사후조건 | 자리가 있었으면: 결과는 OK이고, `elems`는 맨 뒤에 `e`가 붙은 것 |
| 45 | 사후조건 | 가득 찼으면: 결과는 FULL이고, `elems`는 그대로 |
| 46~52 / 53~58 | 본문 / 증명 도우미 | Java 32~34줄을 옮긴 본문 / 26줄이 여전히 맞다는 것을 Dafny가 확인하도록 돕는 부분 |
| 62~67 | `Poll` | Java `poll()`. Java는 비었으면 `null`, 모델은 `(e, ok)`를 돌려주고 비었으면 `ok = false`. 66줄: 비어 있었으면 `elems` 그대로. 67줄: 들어 있었으면 `e` = 가장 오래된 것, `elems`는 맨 앞을 뺀 나머지 |
| 89~92 | `Peek` | `modifies` 줄이 없음 = 아무것도 바꾸지 않음. 들어 있으면 `e` = 맨 앞 |
| 101~117 | 함수 | `Size`, `Capacity`, `IsEmpty`. 값을 계산하기만 하고, 본문 자체가 뜻 |
| 119~133 | `Clear` | 끝나면 비어 있음(123줄). Java처럼 `Poll`을 반복 |
| 135~148 | `Snapshot` | 돌려주는 목록 = `elems` 그대로 |
| 151~173 | 보조정리 | `%` 계산에 대한 사실. 계약이 아님 |

26줄을 그림으로 보면 이렇습니다. 칸 4개짜리 배열에 c, d, e, f가 들었고 `head`가 2인 경우입니다. 배열에서는 e, f가 앞쪽에 있지만, `elems`는 `head`부터 읽어 **c, d, e, f** 순서입니다.

```
칸 번호   0   1   2   3
배열    [ e | f | c | d ]      head = 2, count = 4
elems = [c, d, e, f]           elems[i] == buf[(head + i) % 4]: elems[2] = buf[0] = e
```

44·45줄이 `Offer`의 뜻 전부입니다. 두 줄이 **모든 경우**(자리 있음 / 가득 참)를 나누고, 각각 **결과값**과 **바뀐 뒤의 내용**을 함께 말합니다.

```dafny
ensures old(count) < buf.Length ==> r == OK && elems == old(elems) + [e]     // 44: 자리가 있으면 OK, 맨 뒤에 추가
ensures old(count) == buf.Length ==> r == FULL && elems == old(elems)        // 45: 가득 찼으면 FULL, 내용 그대로
```

**Java와 나란히 놓기.** 어느 Java 줄이 어느 Dafny 줄이 됐는지 봅니다(`legacy/src/main/java/com/dxlab/homehub/queue/RingEventQueue.java`와 `mine/RingEventQueue.dfy`). **옮기면서 달라진 곳**(굵은 글씨)이 판단할 거리입니다.

| Java | Dafny | 같은가 |
|---|---|---|
| 15~17 필드 | 14~17 | 필드 세 개는 그대로. Dafny에는 증명용 `elems`가 더 있음 |
| 30~36 `offer` | 40~52 | 가득 참이면 FULL, 아니면 `(head + count) % 칸 수`에 넣고 `count` 증가: 같음. **Java 31줄 `null` → REJECTED는 모델에 없음.** 모델의 `Event`는 null이 될 수 없는 타입이라 이 경우를 다루지 않음. Dafny에서 null이 될 수 있는 타입은 `Event?`처럼 써야 하고(`?`는 클래스 타입에만 붙일 수 있어 `datatype`인 `Event`는 클래스로 바꿔야 함) |
| 38~45 `poll` | 62~78 | 꺼낸 칸을 비우고 `head`를 한 칸 옮김: 같음. **빈 칸 표시가 다름**: Java는 `null`, 모델은 `Event(0, false)`. 비었을 때의 결과도 Java `null`, 모델 `ok = false` |
| 64~68 `clear` | 119~133 | `Poll`을 빌 때까지 반복: 같음 |
| 70~76 `snapshot` | 135~148 | `head`부터 `count`개를 차례로: 같음 |

**계약 확인 목록.** AI가 만든 모델의 public 메서드마다 아래를 확인합니다. 오른쪽은 이 모델에서 찾은 답입니다.

| 확인할 것 | 빠지면 생기는 일 | 이 모델에서 |
|---|---|---|
| 모든 경우를 다루는가? (자리 있음 / 가득 참, 비어 있음 / 비어 있지 않음) | 다루지 않은 경우에는 아무 동작이나 증명을 통과함 | Offer 44·45줄, Poll 66·67줄: 두 경우 모두 있음 |
| 결과값뿐 아니라 **바뀐 뒤의 내용**까지 말하는가? (`elems == ...`) | FULL을 돌려주면서 내용을 망가뜨려도 통과함 | 44줄 `elems == old(elems) + [e]`, 67줄 `elems == old(elems)[1..]` |
| 바뀌면 안 되는 것이 그대로라고 말하는가? (`elems == old(elems)`) | 위와 같음 | 45줄, 66줄. 43·65줄 `buf == old(buf)` |
| `requires`가 너무 강하지 않은가? | Java에서는 가능한 호출을 모델이 다루지 않게 됨 | Offer는 `Valid()`만 요구(41줄). 만약 "가득 차 있지 않을 때만"을 요구했다면 45줄 경우를 다루지 않는 모델이 됨 |
| 모델 밖으로 둔 동작이 적혀 있는가? (null 입력, 동시성 등) | 무엇을 확인하지 않았는지 모르게 됨 | **빠져 있음.** Java 31줄 `null` → REJECTED를 다루지 않는데 파일 어디에도 적혀 있지 않음. AI에게 `Event`를 `Event?`로 고치고 그에 따라 다른 부분도 고치라고 하거나, 주석으로 null 값은 고려하지 않는다고 남겨야 함 |

### B-2. 계약에서 규칙 R1~R4 찾기 (종이 연습)

**계약 읽는 법.** 사후조건은 두 종류이고, 화살표 방향이 반대입니다.

| 줄 | 형태 | 뜻 |
|---|---|---|
| 105~112 | `r == X <==> (시작 상태 조건)` | 시작 상태(대기열이 찼는지, 중요 이벤트인지, autoDrain이 켜졌는지)를 보면 결과 `r`이 무엇이어야 하는지 정해짐 |
| 113~122 | `r == X ==> (끝난 뒤의 상태)` | 결과가 X였다면, 끝난 뒤 대기열 내용(`queue.elems`)과 처리한 목록(`Dispatched`)이 어때야 하는지 |

예: 대기열에 자리가 있으면, 105줄에 따라 결과는 반드시 `ACCEPTED`이고, 113~114줄에 따라 대기열 내용은 맨 뒤에 `e`가 붙은 것, 처리한 목록은 그대로여야 합니다.

**[직접 확인] 3단계: 질문.** 답을 먼저 적어 본 뒤 펼칩니다.

1. R3과 R4는 각각 어느 줄인가?
2. `RingEventQueue.dfy`의 사후조건 중 "가득 찼을 때" 줄(45줄)을 지우면 어떤 잘못된 구현이 검증을 통과하는가?
3. `Dispatcher.dfy`에서 어느 결과가 나올지 정하는 105~112줄을 모두 지웠다고 하자. 결과별로 바뀐 뒤의 상태를 말하는 113~122줄은 남아 있다. 대기열에 자리가 있는데도 비중요 이벤트를 거부하고(`REJECTED_FULL`) 대기열을 그대로 두는 구현은 검증을 통과하는가?

<details><summary>답</summary>

1. **R3**: 115~117줄(`ACCEPTED_EVICTED`이면 내용은 가장 오래된 비중요 이벤트를 뺀 나머지 + `e`). 113~114줄, 118~120줄도 남은 이벤트의 순서를 그대로 둔다고 말합니다. **R4**: 111~112줄(`REJECTED_FULL`은 가득 찼고, 비중요 이벤트이고, autoDrain이 꺼져 있을 때만).
2. 가득 찼을 때 FULL을 돌려주면서 **대기열 내용을 지우거나 바꾸는** 구현도 통과합니다. "가득 찼으면 내용 그대로"라고 말하는 줄이 없기 때문입니다. B-1 5단계에서 직접 확인한 것입니다.
3. **통과합니다.** 121~122줄은 "`REJECTED_FULL`이면 내용은 그대로"만 말하고, **언제** `REJECTED_FULL`이 나와도 되는지는 말하지 않습니다. R1(칸 수를 넘지 않음)과 R2(중요 이벤트는 거부하지 않음)도 지켜집니다. 105~112줄이 있어야 "같은 입력에는 같은 결과"라고 말할 수 있습니다.

   참고: 105~112줄의 `<==>`를 `==>`로만 바꾸면 결과는 여전히 하나로 정해집니다. 네 조건(자리 있음 / 가득 참·중요·비중요 이벤트 있음 / 바로 처리 / 거부)이 서로 겹치지 않고 모든 경우를 덮어서, 어떤 상태에서든 조건이 맞는 결과가 하나뿐이기 때문입니다.
</details>

**알게 된 것:** 규칙 R1~R4는 Dispatcher 모델의 사후조건으로 적혀 있습니다. "언제 어떤 결과가 나오는가"(105~112줄)와 "그 결과일 때 무엇이 남는가"(113~122줄)가 둘 다 있어야 규칙을 온전히 말합니다.

### B-3. Java에 버그를 넣고 차분 테스트가 잡는지 보기

**이 단계의 질문:** 차분 테스트는 Java의 버그를 정말 잡는가? 무엇을 놓칠 수 있는가?

## C. 테스트를 다 통과한 패치 두 개 판단하기

> **이 실습에서 배울 것: 테스트를 전부 통과한 AI 패치에도 버그가 있을 수 있습니다.** 테스트는 사람이 만든 상황만 확인합니다. Dafny 검증은 **모든 상태**를, 차분 테스트는 **무작위로 만든 많은 상황**을 확인해서, 테스트가 만들지 못한 상황의 버그를 찾습니다.

**상황 (변경 요청 1, 상품기획팀).** "저녁에 이벤트가 몰리면 대기열(8칸)이 가득 차서 이벤트가 거부됩니다. 평소에는 8칸만 쓰고, 필요할 때만 최대 32칸까지 늘려 주세요." AI에게 이 요청을 줬더니 패치 두 개가 나왔습니다. **둘 다 테스트를 전부 통과합니다.** 어느 것을 내보내도 될까요?

**[직접 확인]** 패치 A의 오류를 읽습니다. 112줄은 `Grow`가 끝나는 곳, 지키지 못한 약속은 111줄의 사후조건 `Valid()`, 그 안에서도 44줄 `elems[i] == buf[Wrap(head as int + i)]`(i번째 내용 = 배열의 head+i번째 칸. `Wrap(k)`는 모델 안에서 정의한 함수로 Java의 `k % buf.length`)입니다. 대기열이 한 바퀴 돈 상태에서 A처럼 늘리면 이렇게 됩니다.

```
늘리기 전  (head=2, 내용 c,d,e,f)       [ e | f | c | d ]
패치 A    (자리 그대로, head=2)          [ e | f | c | d | _ | _ | _ | _ ]   head=2부터 c,d,_,_ ← e,f가 사라짐
패치 B    (순서대로, head=0)             [ c | d | e | f | _ | _ | _ | _ ]   head=0부터 c,d,e,f
```

테스트는 빈 대기열에서만 늘려 봤기 때문에 이 상황을 만들지 않았습니다.

<details><summary>자세히: 패치 A는 정확히 무엇이 틀렸나</summary>

두 패치는 배열을 늘리는 `grow()`만 다릅니다(`work/req1-ai-A`, `work/req1-ai-B`의 `RingEventQueue.java` 48줄부터).

| | 코드 | 하는 일 |
|---|---|---|
| 패치 A | `System.arraycopy(buf, 0, bigger, 0, buf.length);` (`head`는 그대로) | 배열을 **칸 번호 그대로** 큰 배열에 복사 |
| 패치 B | `bigger[i] = buf[(head + i) % buf.length];` 반복 후 `head = 0;` | **오래된 것부터 순서대로** 큰 배열 앞쪽에 옮김 |

원형 대기열은 `head`부터 읽다가 배열 끝에 닿으면 앞으로 돌아갑니다. 4칸 대기열에 3, 4, 5, 6이 이렇게 들어 있다고 합시다.

```
늘리기 전 (4칸)  [ 5 | 6 | 3 | 4 ]                  head=2  읽는 순서: 칸2, 칸3, (끝, 앞으로) 칸0, 칸1 = 3, 4, 5, 6
패치 A (8칸)     [ 5 | 6 | 3 | 4 | _ | _ | _ | _ ]  head=2  읽는 순서: 칸2, 3, 4, 5 = 3, 4, 빈칸, 빈칸   ← 5, 6이 사라짐
패치 B (8칸)     [ 3 | 4 | 5 | 6 | _ | _ | _ | _ ]  head=0  읽는 순서: 칸0, 1, 2, 3 = 3, 4, 5, 6        ← 맞음
```

A는 배열이 길어졌는데 칸 번호를 그대로 두었습니다. 그래서 끝을 넘어 앞쪽(칸 0, 1)에 있던 5와 6은 이제 "앞으로 돌아갈 필요가 없는" 자리가 되어, 읽는 쪽은 비어 있는 칸 4, 5로 갑니다. 실제 Java에서는 `poll()`이 3, 4 다음에 `null`을 돌려줍니다.

**테스트가 통과한 이유.** 두 패치가 더한 테스트는 빈 대기열에 넣기만 하면서 늘립니다. 그때는 `head`가 0이고 끝을 넘어 앞으로 돌아간 이벤트가 없으므로, 칸 번호 그대로 복사해도 결과가 맞습니다. 버그는 앞쪽을 몇 개 꺼내서 `head`가 0이 아니고 대기열이 끝을 넘어 감긴 상태에서 늘릴 때만 드러납니다.

</details>

<details><summary>자세히: 원본의 계약(사전·사후조건)을 어긴 수정인가</summary>

거의 맞습니다. 정확히는 원본 모델에서부터 있던 **불변식**이 깨졌고, 그 때문에 원본과 같은 `Offer`의 사후조건도 지킬 수 없게 됩니다.

1. **깨진 것은 불변식입니다.** "i번째 내용 = 배열의 (head+i)번째 칸"이라는 줄은 원본(`formal/RingQueue.dfy` 37줄)과 두 패치의 모델(`RingQueue_A.dfy` 44줄, `RingQueue.dfy` 38줄)에 똑같이 있습니다. 메서드 하나의 조건이 아니라 대기열 객체가 늘 지켜야 하는 약속이어서, 모든 메서드가 이것을 전제로 시작하고(`requires Valid()`) 끝날 때 다시 지켜야 합니다(`ensures Valid()`). 패치 A의 `Grow`는 끝날 때 이것을 지키지 못합니다.
2. **그래서 `Offer`의 약속도 깨집니다.** 패치 모델의 `Offer` 계약은 원본과 같고, 승인된 변경인 상한만 `MaxCapacity()`(32)로 바뀌었습니다: `ensures |old(elems)| < MaxCapacity() ==> r == OK && elems == old(elems) + [e]`(자리가 있으면 OK, 내용은 기존 + e). `Offer`는 가득 찼을 때 안에서 `Grow()`를 부르므로, `Grow`가 배열과 내용의 대응을 깨면 "기존 + e"가 되지 않습니다. 사용자 입장에서는 "넣은 이벤트가 순서대로 남는다"는 원래 약속을 어긴 것입니다.
3. **계약이 틀린 것은 아닙니다.** 같은 계약을 패치 B의 본문은 지키고 검증을 통과합니다. 틀린 것은 A의 본문입니다. B-1 5단계(계약이 약하면 틀린 모델도 통과)와 반대되는 경우입니다.

정리하면 패치 A는 요청이 허락한 변화(상한 8 → 32)만 한 것이 아니라, 원본이 지키던 "대기열의 내용과 순서가 유지된다"는 약속까지 깨뜨린 수정입니다.

</details>

### C-4. 테스트가 놓친 상황을 직접 테스트로 쓰기

**이 단계의 질문:** 그 상황을 알고 나면 테스트로 잡을 수 있는가?

## D. 재검증 범위 줄이기

> **이 실습에서 배울 것: 코드가 바뀌어도 Dafny 증명을 전부 다시 할 필요는 없습니다. 무엇이 바뀌었느냐에 따라 다시 증명할 범위가 정해지고, 그 범위는 Java 영향 분석의 범위와 다릅니다.**

Dafny는 메서드를 하나씩 증명하고, 다른 메서드를 부를 때는 **그 메서드의 계약만** 봅니다. 그래서 다음 규칙이 나옵니다.

| 메서드 계약 | 그 메서드 + 부르는 메서드 |

Java가 바뀌면 Dafny 모델도 새 코드대로 고쳐 둡니다. 모델을 고치는 일은 [AI 몫](P-3)입니다. D-1과 D-2에서 각각 모범 답안(`scenarios/req*/model/`)을 쓰거나 Codex에게 고치게 합니다.

### D-1. 변경 요청 2, 본문만 바뀐 경우

**요청 (플랫폼팀).** "허브 칩에서 나눗셈(`%`)이 느리니, 대기열 `RingEventQueue`에서 `%`를 없애 달라. `clear()`는 `poll()`을 반복하지 말고 한 번에 비워 달라. 동작은 바꾸지 말 것." AI는 Java 메서드 **네 개의 본문**을 고쳤습니다.

| 메서드 | 레거시 | 변경 요청 2 |
|---|---|---|
| `offer` | `buf[(head + count) % buf.length] = e` | `idx = head + count`, 끝을 넘으면 `idx -= buf.length` |
| `poll` | `head = (head + 1) % buf.length` | `head++`, 끝에 닿으면 `head = 0` |
| `snapshot` | `buf[(head + i) % buf.length]`를 차례로 담음 | `idx`를 하나씩 늘리다 끝에 닿으면 0 |
| `clear` | 빌 때까지 `poll()` 반복 | `Arrays.fill(buf, null); head = 0; count = 0` |

**[AI 몫]** 변경 요청 2에 맞춘 대기열 모델을 준비합니다.

재검증 도구는 바뀐 기호를 세 가지로 나눕니다.

| 표시 | 무엇이 바뀌었나 | 다시 증명할 것 |
|---|---|---|
| `body` | 메서드 본문(`{ }` 안)만 | 그 메서드만. 부르는 쪽은 계약만 봤으므로 그대로 |
| `contract` | `requires`, `ensures`, `modifies`, `reads`, `decreases`, 시그니처 | 그 메서드 + 본문에서 그것을 부르는 메서드 |
| `definition` | 함수·술어(`Valid`, `Inv`처럼 참/거짓이나 값을 돌려주는 것)의 정의 | 그것을 언급하는 기호 전부 |
| `added` | 새로 생긴 기호(`Grow`, `MaxCapacity`) | 그 기호 |

</details>

<details><summary>자세히: `Inv`를 언급하기만 해도 다시 증명하는 이유</summary>

`Inv`나 `Valid` 같은 술어는 메서드와 달리, 그것을 쓰는 증명 안에서 **정의가 펼쳐져** 쓰입니다. 예를 들어 `Size`의 증명은 "`Inv`가 참이면 이러저러하다"를 `Inv`의 정의를 보고 따집니다. 그래서 `Inv`의 정의가 바뀌면, 본문과 계약이 그대로인 `Size`, `Peek`, `IsEmpty`도 그 증명이 여전히 맞는지 다시 확인해야 합니다. (정의를 감춰 둔 `opaque` 함수는 예외로, `reveal`한 곳만 다시 증명합니다.)

</details>

**알게 된 것:** 대기열 계약이 바뀌었으므로, 대기열 대부분과 그 계약을 믿고 증명된 Dispatcher까지 다시 증명합니다.

### D-3. Java 영향 분석과 비교하기

**이 단계의 질문:** Java 영향 분석의 범위와 Dafny 재검증의 범위는 왜 다른가?

**[직접 확인]** 처음의 표를 채웁니다.

| 변경 | 바뀐 것 | Java 영향 분석 | Dafny 다시 증명 |
|---|---|---|---|
| 요청 2 | 메서드 본문만 | 메서드 79개 | 49개 중 4개 (바뀐 본문) |
| 요청 1 (패치 B) | 대기열의 계약 | 메서드 128개 (`out/impact-req1-ai-B.md`의 "3. 출력이 달라질 수 있는 메서드 (128)") | 51개 중 19개 (대기열 + 그 계약을 믿은 Dispatcher) |

`out/reverify-req1.md`의 끝("Java impact analysis vs. Dafny proof dependencies")에는 두 범위가 어긋나는 곳이 나옵니다.
- **Java 영향에는 있지만 다시 증명할 필요 없음 (8개)**: 전력 모델의 메서드들(`TryStart`, `Stop` 등). Java에서는 대기열에서 꺼낸 이벤트가 전력 승인까지 흘러가므로 "달라질 수 있다"고 보지만, 전력 모델의 증명은 대기열을 보지 않습니다.
- **다시 증명해야 하지만 Java 영향에는 없음 (6개)**: `Valid`, `Inv`, `MaxCapacity`, `Grow` 등 계약과 정의에만 쓰이는 것. Java 코드에는 대응하는 메서드가 없습니다.

**알게 된 것:** Dafny는 다른 메서드를 부를 때 그 메서드의 **계약만** 봅니다. 본문만 바뀌면 그 메서드만, 계약이 바뀌면 부르는 쪽까지 다시 증명합니다. Java 영향 분석은 값이 흘러가는 곳을 모두 세므로 더 넓습니다.

<details><summary>자세히: 그럼 Java 영향 분석과 Dafny 재검증 중 어느 쪽이 맞나</summary>

둘 다 맞습니다. 묻는 것이 다릅니다.

- **Java 영향 분석**: "바뀐 코드에서 나온 값이 흘러가서, 이 메서드의 출력이 **달라질 수 있는가**?" 요청 2에서 대기열에서 꺼내는 이벤트가 Dispatcher와 전력 승인까지 흘러가므로 79개가 됩니다. 실제로 그 메서드들의 출력이 달라지지 않더라도(요청 2는 동작을 바꾸지 않음) 값이 흐르면 셉니다.
- **Dafny 재검증**: "이 메서드의 **증명이 여전히 성립하는가**?" Dispatcher의 증명은 대기열 코드가 아니라 대기열의 계약만 보고 이뤄졌습니다. 계약이 그대로면 대기열 코드가 어떻게 바뀌어도 Dispatcher의 증명은 그대로입니다.

Dafny 쪽이 좁을 수 있는 것은 계약이 있고, 그 계약을 대기열이 지킨다는 것이 증명돼 있기 때문입니다. Java 코드에는 그런 계약이 적혀 있지 않으므로 영향 분석은 값이 흐르는 곳을 모두 따라갈 수밖에 없습니다.

</details>

**생각해 볼 것.** Java 영향 분석의 범위와 Dafny 재검증 범위가 다른 이유를 한 문장으로 설명해 보세요.

## E. 정리 규칙을 코드 전체에 적용하기

> **이 실습에서 배울 것: 조건부 규칙을 적용하는 곳에서 조건을 누락하면 잘못된 결과가 나옵니다.**

**왜 정리하나요.** 오래된 Java 코드에는 지금 보면 번거로운 옛 방식이 많습니다. 목록이 비었는지 `size() == 0`으로 묻고, 목록을 돌 때 인덱스 `i`를 쓰고, 한 번만 쓰는 임시 변수를 따로 둡니다. 이런 곳을 같은 뜻의 더 읽기 쉬운 코드로 바꾸는 것이 코드 정리(리팩터링)입니다. 같은 모양이 코드 곳곳에 있으므로 보통은 "이 규칙을 코드 전체에 적용해 줘"라고 도구나 AI에게 맡깁니다. "같은 뜻으로 바꾸기"라서 안전해 보이기 때문입니다.

**하지만** 대부분의 정리 규칙은 **어떤 조건에서만** 같은 뜻입니다. 코드 전체에 일괄 적용하는 도구나 AI는 그 조건을 자리마다 확인하지 않을 수 있습니다.

**이 실습의 규칙 세 개.** 예는 HomeHub 코드에서 실제로 바뀌는 곳 하나씩입니다.

| 규칙 | 바꾸기 전 | 바꾼 뒤 |
|---|---|---|
| ① 비었는지 묻기: `size() == 0` → `isEmpty()` | `return running.size() == 0;` (`PowerBudget.isIdle`) | `return running.isEmpty();` |
| ② 인덱스 반복 → for-each | `for (int i = 0; i < derived.size(); i++) { dispatcher.submit(derived.get(i)); }` (`HomeHub.flushDerived`) | `for (Event d : derived) { dispatcher.submit(d); }` |
| ③ 변수 인라인: 한 번만 쓰는 지역 변수를 그 식으로 바꿈 | `String line = tag + ...; entries.add(line);` (`AuditLog.record`) | `entries.add(tag + ...);` |

**순서.** E-1에서 규칙마다 조건을 적고 → E-2에서 AI가 코드 전체에 적용한 결과를 세 가지로 확인하고, 동작이 바뀐 곳의 원인을 찾아 직접 따라가 보고 → E-3에서 조건이 정말 필요한지 Dafny로 확인합니다.

### E-3. 조건을 Dafny로 증명하고, 조건을 지워 보기

**이 단계의 질문:** E-1에서 적은 조건이 정말 필요한가?

정리 규칙이 "같은 뜻"이라는 것을 Dafny로 이렇게 적습니다.

1. 바꾸기 **전**의 코드와 바꾼 **뒤**의 코드가 하는 일을 각각 Dafny 함수로 적습니다.
2. "두 결과가 같다"를 보조정리(`lemma`)의 사후조건(`ensures`)으로 적고 증명합니다. 이것이 `<규칙>_Same`입니다.
3. 같아지려면 필요한 **조건**은 그 보조정리의 사전조건(`requires`)으로 적습니다. 이것이 E-1에서 적은 "같은 뜻이 되는 조건"입니다.
4. 조건부 규칙은 "조건이 없으면 두 쪽이 다르다"는 구체적인 예도 증명해 둡니다. 이것이 `<규칙>_Counterexample`입니다.

세 규칙이 모두 `rewrite/RewriteRules.dfy` 한 파일에 있습니다.

**[직접 확인]** `rewrite/RewriteRules.dfy` 99~104줄이 변수 인라인 규칙의 "같다" 증명입니다. 100줄 `requires`가 E-1에서 적은 조건입니다.

```dafny
  lemma InlineVariable_Same<S>(s: S, size: S -> nat, body: S -> S)
    requires forall t :: size(body(t)) == size(t)        // condition: the body does not change e
    ensures Fixed(s, body, 0, size(s)) == Inlined(s, size, body, 0, size(s))
```

`Fixed`는 바꾸기 전 코드(`n`을 반복 전에 한 번 잼), `Inlined`는 바꾼 뒤 코드(반복할 때마다 `queue.size()`를 다시 잼)를 나타내는 함수입니다. `requires` 줄이 규칙의 조건(반복 본문이 크기를 바꾸지 않음)입니다.

먼저 세 규칙의 증명을 검증합니다. 예상: `15 verified, 0 errors`.

### 조건을 확인하면서 적용하는 도구

조건부 다시쓰기 규칙을 표현하는 도구들이 있습니다. 조건을 어디까지 표현하는지가 다릅니다.

| 도구 | 조건을 거는 방식 |
|---|---|
| Spoon (Java) | 변환을 Java 코드로 쓰고, 조건도 코드로 검사. 필요한 분석은 직접 구현 |
| Error Prone + Refaster (Java) | 바꾸기 전·후 모양을 템플릿으로 쓰고, 패턴 변수에 판별기를 붙임. 검사기에서는 null 분석 같은 값 흐름 분석 결과를 쓸 수 있음 |
| Semgrep (여러 언어) | 패턴 + 제외 조건 + 자동 수정. 메서드 안의 값 흐름 추적 |
| IntelliJ 구조 검색·바꾸기 (Java) | 패턴 변수마다 타입, 정규식, 스크립트 조건 |
| Coccinelle (C) | 의미 패치에 실행 경로 조건(`when`)을 걺 |
| Rascal, Stratego, TXL | 조건부 다시쓰기 규칙과 적용 전략을 일반적으로 표현 |

변수 인라인의 조건("쓰는 동안 값이 안 바뀜")을 확인하려면, 반복문 안에서 `queue.size()`의 값을 바꾸는 호출(`poll`)이 있는지 알아야 합니다. 값이 어디서 바뀌는지 메서드를 넘어 따라가는 **값 흐름 분석**이 필요합니다. 도구가 조건을 표현할 수 있어도, 조건의 판단은 그 분석이 얼마나 정확한가에 달려 있습니다. 그래서 적용한 뒤 동작을 비교해 확인합니다.

## 끝나고 정리하기

`work/`, `build/`, `out/`, `legacy/build/`, `mine/`에는 저장소에 들어 있던 모범 답안 결과도 함께 있습니다. 그래서 `rm -rf`로 폴더째 지우지 않고, git으로 실습 전 상태로 되돌립니다. 명령은 macOS와 Windows cmd에서 같습니다.

1. 무엇이 바뀌었는지 봅니다: `git status --short work build out legacy mine rewrite`
2. 바뀐 파일을 저장소 상태로 되돌립니다(실습 중 고친 `legacy/`, `rewrite/`도 함께 되돌아감): `git checkout -- work build out legacy mine rewrite`
3. 실습 중 새로 생긴 파일을 확인합니다(아직 지우지 않음): `git clean -n work build out legacy mine rewrite`. 보통 `work/my-*` 폴더와 `out/` 아래의 보고서입니다. 남겨 두고 싶은 파일이 있으면 이 폴더들 밖으로 옮겨 둡니다.
4. 확인한 것을 지웁니다: `git clean -fd work build out legacy mine rewrite`
5. `git status --short work build out legacy mine rewrite`가 아무것도 출력하지 않으면 끝입니다.

**git이 없거나 위 명령이 안 될 때: 0-0의 백업으로 되돌리기.** 여섯 폴더를 지우고 백업을 다시 복사합니다. 실습 중 새로 만든 파일(`work/my-*` 등)도 함께 지워지므로, 남길 것은 먼저 이 폴더들 밖으로 옮겨 둡니다.

```
rm -rf work build out legacy mine rewrite && cp -R _backup/. .
```

cmd (두 줄):
```
for %d in (work build out legacy mine rewrite) do if exist %d rmdir /s /q %d
for %d in (work build out legacy mine rewrite) do xcopy /e /i /q _backup\%d %d
```

되돌린 뒤에도 `_backup/`은 남아 있으므로, 실습을 다시 할 때 또 쓸 수 있습니다. 필요 없으면 `_backup/`을 지웁니다. 백업을 하지 않았고 git도 없다면 실습 폴더를 다시 받습니다.
