## 1. 과정과 실습의 대응

| 세션 | 시간 | 실습 | 핵심 메시지 |
|---|---|---|---|
| 1 개요 | 30분 | 없음 | AI는 레거시 코드를 잘 고친다. 문제는 "고친 것이 기존 동작을 지켰는가"를 무엇으로 확인하느냐다. |
| 2 구조·의존성·변경 영향 | 150분 | 구조 지도 (15분, 0_시작하기), A (40분) | 처음 보는 코드는 구성 요소와 메시지 하나의 길부터 본다. 바뀐 줄에서 나온 값이 어디까지 흘러가는지(def-use)를 따라가 영향 범위를 구한다. 결과는 "달라질 수 있다"이고, 라이브러리가 대신 부르는 코드는 못 따라간다. |

| 5 검증 비용 줄이기 | 90분 | D (20분), E (35분) | 바뀐 것의 종류(본문/계약)로 다시 증명할 범위가 정해진다. 조건부 정리 규칙을 조건이 깨지는 곳에 적용하면 동작이 바뀐다. |
| 6 최신 연구 | 80분 | 없음 | 제약 디코딩(생성 단계에서 막기), LLM+정적분석 허위 경보 분류, equality saturation |

- **Dafny 기준 모델이 Java와 똑같이 `%`를 씁니다.** 이전에는 모델이 `%` 대신 조건식을 써서, 변경 요청 2에서 Java는 4개 메서드가 바뀌는데 Dafny는 Clear 하나만 바뀌는 어색함이 있었습니다. 지금은 "바뀐 Java 메서드에 대응하는 Dafny 메서드를 새 Java 코드대로 다시 옮긴다"는 규칙 하나로 통일했고, 변경 요청 2에서 Dafny도 4개 본문이 바뀝니다. `%`에 대한 사실은 `Types.ModWrap` 보조정리 하나로 증명하고 `Wrap` 함수의 사후조건으로 노출해서, 다른 증명은 나눗셈을 다루지 않습니다.

- A-1 수치(변경 요청 2): 데이터 24개, 메서드 79개, 테스트 33/38. AI와 비교하면 AI는 대기열을 직접 쓰는 Dispatcher 정도는 잘 짚지만, 꺼낸 이벤트가 기기 상태·전력·로그까지 흘러가는 것과 테스트 목록은 빠뜨리기 쉽습니다.

### 실습 B

- B-1: AI마다 결과가 다릅니다. 자주 나오는 문제는 (1) FULL일 때 내용이 그대로라는 사후조건 누락, (2) `requires !Full()`처럼 Java에서 가능한 호출을 막아 버리는 사전조건, (3) null 입력을 말없이 빼 버림, (4) 검증이 어려우면 `assume`이나 `{:verify false}`로 넘어감. (4)는 검증 출력에 경고가 나오므로 확인시킵니다.
- 예시 답(`scenarios/b1-ai-sample`)은 AI가 쓸 법한 모양으로 만든 것입니다. Java의 `REJECTED`(null 입력)를 datatype에는 넣었지만 돌려주는 경우가 없고, 그 사실이 주석에도 없습니다. "모델 밖 동작이 적혀 있는가" 항목에서 짚을 수 있습니다.
- B-2 답 (줄 번호는 노트북 답 보기에 있음)
  1. R3: `ACCEPTED_EVICTED ==> elems == Remove(...) + [e]` 줄(그리고 `ACCEPTED`, `ACCEPTED_DRAINED`의 내용 줄. 모두 남은 것의 순서를 유지함). R4: `REJECTED_FULL <==> ... && !e.critical && !autoDrainOnFull`.
  2. FULL일 때 대기열 내용을 지우거나 바꾸는 구현, 또는 가득 찼는데 OK를 돌려주는 구현도 통과합니다.

## 5. 수업에서 자주 나올 질문

- **"Dafny 모델을 AI가 만들면, 모델이 틀렸을 때는?"** 세 겹으로 막습니다. 사람이 계약을 읽고, 차분 테스트로 모델과 Java를 비교하고, 모델 밖 영역을 적어 둡니다. 어느 것도 완전하지 않습니다. 그래서 "Java가 검증됐다"고 말하지 않고 "모델과 계약이 검증됐고, 모델과 Java는 이 입력 범위에서 일치한다"고 말합니다.
- **"Java가 바뀔 때 Dafny는 누가 고치나?"** 바뀐 Java 메서드에 대응하는 Dafny 메서드를 AI가 새 Java 코드에서 다시 옮깁니다(P-3). 계약은 요청서가 승인한 만큼만 바뀝니다. 그다음 재검증 범위를 계산해 그 부분만 증명하고, 차분 테스트로 새 Java와 새 모델을 비교합니다.
- **"C/C++ 코드에는?"** 같은 흐름이 그대로 적용됩니다. def-use 분석은 clang/LLVM 기반 도구로, 차분 테스트는 C++ 하네스로 만듭니다. Java를 고른 이유는 Dafny Java 백엔드가 있고, javap만으로 분석 도구를 만들 수 있어서입니다.
- **"테스트를 더 잘 쓰면 되지 않나?"** 패치 A의 버그는 "한 바퀴 돈 상태에서 늘리기"라는 특정 상태 조합에서만 나타납니다. AI가 추가한 테스트도 그 조합을 만들지 않았습니다. 계약은 모든 상태를 다루고, 차분 테스트는 상태 조합을 무작위로 많이 만들어 냅니다.

## 6. 알려진 한계 (질문이 나오면 그대로 답하면 됨)

- 영향 분석의 방법 (`tools/defuse.py`, `tools/sdg.py`, `tools/impact.py`)
  - 메서드마다 바이트코드 명령어를 노드로 하는 의존 그래프(PDG)를 만듭니다. 데이터 의존은 지역 변수와 피연산자 스택을 따라, 제어 의존은 사후 지배자(post-dominator)로 구합니다. catch 블록은 try 안에서 예외를 던질 수 있는 명령어에 제어 의존합니다.
  - 필드와 "필드에 담긴 배열·컬렉션의 내용"을 전역 변수처럼 다룹니다. 메서드마다 (자기가 부르는 메서드까지 포함해) 읽는 전역에 formal-in, 쓰는 전역에 formal-out 노드를 두고, 호출 지점마다 actual-in/out 노드를 둡니다. 호출 → 피호출 메서드 시작, actual-in → formal-in, formal-out → actual-out으로 이어 프로그램 전체 의존 그래프(SDG)를 만듭니다.
  - 호출 지점마다 summary 간선(피호출 메서드 안에서 formal-in이 formal-out에 닿으면 actual-in → actual-out)을 작업 목록 알고리즘으로 구합니다(이 패키지에서 약 8만 개, 1초 안팎).
  - 전방 슬라이스는 2단계입니다. 1단계는 데이터·제어·summary·parameter-out 간선(부른 쪽으로 올라감)만, 2단계는 1단계에서 닿은 모든 노드에서 데이터·제어·summary·호출·parameter-in 간선(부르는 메서드로 내려감)만 따라갑니다. 그래서 호출과 반환의 짝이 맞지 않는 경로는 따라가지 않습니다.
  - 프로그램 안에서 아무도 부르지 않는 메서드(테스트, main, 외부에서 부르는 API)는 바깥에서 어떤 순서로든 불릴 수 있다고 보고, 그런 메서드가 쓴 전역을 그런 메서드 모두가 읽을 수 있게 이어 둡니다.
  - "메서드가 실행되는가"(진입 노드)에는 부작용(필드·배열 쓰기, 호출)만 의존합니다. 값은 의존하지 않습니다: 어떤 메서드가 불릴지 말지가 달라져도, 불렸을 때 돌려주는 값은 그대로이기 때문입니다.
  - 보고서의 이유 경로는 슬라이스 안의 최단 경로이며, summary 간선은 피호출 메서드 안의 줄로 펼쳐 보여 줍니다. "바깥에서 다시 불림"을 거치는 경로는 다른 경로가 없을 때만 고릅니다.
- 영향 분석의 한계
  - 필드는 객체를 구분하지 않고 이름으로만 구분합니다(같은 클래스의 두 객체의 필드를 하나로 봄). 그래서 넓게 잡습니다. 인자로 받은 객체의 내용을 피호출 메서드가 바꾸는 것도 필드 이름 단위로만 봅니다.
  - JDK 코드는 분석하지 않습니다. 라이브러리 호출의 결과는 수신 객체·인자·수신 객체 내용에 의존한다고 보고, 읽기 전용으로 알려진 메서드가 아니면 수신 객체의 내용을 바꾼다고 봅니다. 라이브러리가 대신 부르는 콜백은 놓칩니다(A-2 ②).
  - JDK가 던지는 예외(`NullPointerException` 등)는 같은 메서드의 catch 블록에만 반영하고, 메서드 밖으로 나가는 예외로는 보지 않습니다. 예외 때문에 이후 코드가 건너뛰어지는 효과도 따지지 않습니다. 프로그램이 직접 던지는 예외(`throw`)와 그것이 호출을 거쳐 나오는 것은 따라갑니다.
  - 리플렉션, 람다(invokedynamic)의 호출 대상, 설정 파일은 따라가지 않습니다.
  - 테스트 코드의 변경은 다시 돌릴 테스트만 정하고, 제품 코드의 영향으로 세지 않습니다. 테스트가 계산해 제품 메서드에 넘기는 인자도 제품 코드의 영향으로 세지 않습니다.
- `tools/reverify.py`: Dafny 소스 형식을 가정합니다(본문 여는 중괄호가 줄 끝이나 단독 줄). 이름이 애매하면 넓게 잡습니다. Dafny 자체의 증명 캐시는 쓰지 않습니다.
- `difftest`: 무작위 표본입니다. 큐 용량 4, 연산열 길이 60, 300회가 기본값입니다.
- 모델 밖: null 입력, 동시성, 핸들러·지표·감사 로그 부작용, long 범위 seq.
